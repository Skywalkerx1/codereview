## Proposal — a rebuttal-precedent mechanism (for [2]; proposal only, decision reserved)

**Problem.** A rebuttal sustained with evidence currently lives only as prose in a dispositions file inside the next reviewed span. Fresh panels judge the diff in front of them and — defensibly, for an independent gate — do not treat a builder-authored in-diff document as authority. The result: settled substance is re-raised every round (v9 → v11 [36]–[39] → v12 [2] + [10]/[11]/[15], the same POSIX guard four times), spending panel findings and adjudication time, while the naive fixes (deleting the guard, renaming to evade the deterministic rule, excluding the path) would all be the gate being gamed.

**Proposal: precedent records, machine-checked like fixture scope.**
1. **A versioned precedents file** (e.g. `review-precedents.json`, schema-versioned like the fixture manifest). Each entry names: a finding **fingerprint** (rule/category + a content hash of the flagged line(s) as they exist in the tree — content-addressed, never line-number-addressed), the rebuttal summary, the evidence pointer (dispositions file + commit), and the **sustaining event** (see 3).
2. **Classification, not suppression.** On a record run that declares the precedents file, a finding whose fingerprint matches a live precedent is presented in a separate `precedent_findings` list — evidence and counts preserved in the record, exactly like `fixture_findings` — instead of blocking as a fresh finding. The raw review artifact is never altered; without a declared precedents file, nothing changes.
3. **Finder-confirmation mints precedents; builders cannot self-mint.** A precedent is created only when a rebuttal has been sustained through a verification round in which the seat that raised the original finding is among the reviewers confirming it (the existing finder-confirmation rule), or by an owner-recorded decision. A dispositions file alone — builder prose — mints nothing.
4. **Content binding + expiry.** A precedent binds only **byte-identical** flagged content: change the guarded line and the fingerprint stops matching, so the question re-opens automatically. Precedents lapse at the next minor release unless re-sustained. `record-verify` recomputes precedent fingerprints against the recorded head (mirroring `fixture_scope_valid`): a stale or mismatched precedent fails verification rather than silently shielding changed code.
5. **Panel visibility.** The precedents in force are passed to panels as context with their sustaining events named, so a reviewer who still believes the substance is wrong can say so against the *precedent* — a finding that then goes to the owner as a precedent challenge, not as adjudication round five of the same line.

**Alternatives considered.** In-code suppression comments on the flagged line: rejected as the default — they edit the very line under dispute, and they travel with copies of the snippet (the guard line quoted inside old review records would inherit the suppression). Dispositions-as-context only: the status quo — v12 is the proof it does not bind. Deterministic-rule exception list: a skip list by another name, with no sustaining event and no content binding.

**Decision reserved.** Whether to build this before the next closing attempt or accept repeats as the standing cost of an independent panel is the owner's call (the issue report's Option 2 records the trade-off: building it enlarges exactly the surface the next attempt must certify). This round builds nothing of it.
