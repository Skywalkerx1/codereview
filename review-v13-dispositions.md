## The rebutted majors

**[0] `fb58dad35b96` and [1] `e56d2d141503` — the corpus directories the panel says are missing from the patch are in the patch, on disk, and behind a loader that refuses any disagreement.** The panel's claim: `bench/corpus/manifest.json` (a stub whose only content is the ids array) "lists … case ids … for which this patch adds no directories", so "the checked-in corpus is incomplete and `load_corpus` will reject it", breaking the Epic A benchmark. Checked three ways:

- *On disk*: the shipped manifest lists **36** case ids; `bench/corpus/` contains exactly those **36** directories — zero missing, zero extra — each holding `case.json` + `diff.patch`.
- *In the reviewed patch itself*: `git diff --name-only 3013656..1f4c38d -- bench/corpus` lists **73** files (36 cases × 2 + the manifest). Every one of the ten ids [1]'s evidence names — `secret-hardcoded-api-key`, `secret-private-key`, `sql-injection-fstring`, `race-counter-increment`, `ssrf-fetch`, `sensitive-data-logging`, `unbounded-query`, `real-buggy-alert-flood`, `secret-aws-key`, `sql-injection-concat` — has **both** its `case.json` and its `diff.patch` added in the patch, and the record's own `files` array contains all of them. The panel's premise is factually wrong about the artifact it reviewed; the most plausible mechanism is per-batch truncation of the 401,747-character patch (at the 80,000-char default budget, `manifest.json` and the case directories land in different review batches).
- *The invariant is enforced exactly as the README states*: `load_corpus` (bench.py) compares manifest ids against on-disk directories and raises `ValueError` naming the manifest-only and dir-only ids when they disagree — and `tests/test_bench.py::test_shipped_corpus_loads_and_is_balanced` loads the **shipped** corpus through it, asserting ≥ 30 cases with a public/holdout split. The regression test [0] recommends adding ("assert manifest/corpus agreement for the shipped corpus") already exists and runs in every suite. Rebutted for both findings.

**[2] `ef8b8b9ca701` — a bench config rename cannot resurrect stale records; the name is inside the hashed config identity.** The finding reasons from the dedup set `done = {(r["config"], r["case_id"])}` in isolation and concludes a rename desynchronizes it. That key is never reached with foreign records, because `run_bench` filters stored records **before** building `done`: a stored record survives only if its `patch_sha256` equals the case's current diff hash **and** its `config_sha256` equals `_config_sha(cfg)` — and `_config_sha`'s identity dict includes `"name"` (with `providers`, `seat_meta`, `allow_major`, `strict`, `cost_per_call_usd`). A rename therefore changes the hash by construction; the stale records are dropped and the file rewritten without them before dedup is computed, and the results path itself (`<out>/<cfg['name']>.jsonl`) is derived from the same name. The finding's precondition — "an otherwise identical config_sha256" across a rename — cannot occur: identical sha requires identical name, and identical name makes every retained record's `config` field equal to `cfg['name']`. Executable evidence: a probe drove the strongest form of the claim — records written under config `alpha` copied into renamed config `beta`'s own results file — and the run dropped them as stale and re-ran the case exactly once (1 record, `config: "beta"`); a same-name resume appended nothing. The invariant is now pinned as a characterization test (`tests/test_v092_fixes.py::BenchResumeRenameTests`) so it cannot rot silently. Rebutted.

**[3] `9a34f77ec4d6` — fixture path matching is boundary-aware in both branches; the panel's sibling-prefix mechanism cannot fire.** The finding claims plain directory patterns match by naive string prefix, so a product path sharing a prefix with a fixture path could be classified away (or the reverse). The actual code (`core.path_matches`, core.py) uses the same boundary-aware test in **both** the `/**` branch (`base = pat[:-3]`) and the plain branch (`base = pat.rstrip("/")`): `path == base or path.startswith(base + "/")`. The character after the base must be `/`; `bench/corpusx/diff.patch` does **not** match pattern `bench/corpus/**` — a fact already pinned by test since v0.9.0 (`tests/test_v090_fixes.py::PathMatchTests::test_directory_glob` asserts exactly that sibling is False). Further: the shipped manifest denotes directories **explicitly** — all 36 corpus entries carry the `/**` suffix, which is precisely the form the finding's recommendation demands ("represent directories explicitly or require a following slash"); its only plain entries are three exact files (`bench/scripts/{oracle,noisy,blind}.json`). Executable evidence: an adversarial probe over all **39** shipped patterns — every genuine child classified, every sibling mutation rejected (`base + "x/…"`, `base + "-evil/…"`, `base + "2"`, file `base + ".bak"`), product paths never classified — now pinned in `tests/test_v092_fixes.py::FixtureSiblingTests`. One boundary is stated precisely rather than waved away: a plain *file* pattern would also prefix-match a hypothetical `bench/scripts/oracle.json/…` path. Git cannot produce such a path in a tree where `oracle.json` is a file (a tree entry cannot be both a blob and a directory), classification inputs are git patch paths, and the nested channel is additionally guarded by `_fixture_inner_paths`' internalized top-level subtraction (v12 [8]). Rebutted.

## The owner-reserved major

**[4] `a5b9d8c19af3` — OWNER DECISION, PENDING. Decision memo (builder does not implement enforcement and does not record an accept).**

*What the policy currently is.* The free-tier data policy (clean-gate solution §4.6) is implemented as `core.check_tier_policy(seat_meta, private=...)`: a seat explicitly tagged tier `free` must not review a **private** repository, because free tiers may use submitted content to improve the provider's products. Only an explicit `free` tier violates; `unknown` is recorded in the run report, never blocked. Enforcement today is at **run time**: `--private` makes `cli.main` abort with exit 2 **before any review** if a free-tier seat is configured (cli.py: the policy check immediately follows seat construction). The gate attempts do not run with `--private`, and every attempt's tiers are recorded openly in `gate-attempts.md` (the standing panel: Gemini/NVIDIA free as primaries, OpenAI paid as the correctness fallback).

*What the finding asks.* `verify_record`'s `two_families` check reads only the `family` strings of successful reports — no tier condition — so a record does not fail eligibility for having used free-tier seats. The panel recommends failing the record when a successful report has tier `free` "for a private repository", or recording and verifying an explicit private flag.

*The mechanical problem.* A record cannot currently support that check: reports carry `family` and `tier` per seat, but **no `private` declaration exists anywhere in the record schema** (verified: zero occurrences of `"private"` in the v13 record JSON). The policy is a conjunction — free tier **and** private repo — and the artifact contains only one conjunct. `record-verify` forced to guess the other conjunct must either assume every repo is private (every attempt in the ledger becomes retroactively ineligible — attempts 1–6 ran on Gemini-free, attempts 7–9 served operations on NVIDIA-free — and no future record could ever be eligible on the owner's configured panel unless every seat were paid) or assume none are (the check is vacuous). A meaningful verify-time check requires a schema change first: record the run's privacy declaration at run time, then verify against it.

*Options.*
1. **Enforce in `record-verify`** (with the schema change): the strongest machine guarantee. But it folds a *data-protection* policy into the record's *eligibility* bar, which is a verdict-integrity claim. It also produces a paradox for the release record specifically: the record certifies a span of a repository being prepared for public open-source release — once announced, the code is public, and what a free tier saw is the same code anyone can download. The harm the policy guards against (private code entering a provider's training data) does not map onto a public-release record.
2. **Run-time enforcement only (status quo)**: the operator — the only party who knows the repository's status — declares `--private` and the run refuses free seats before any code is sent. `record-verify` stays a pure function of the artifact. Weakness: an operator can omit `--private` on a genuinely private repo. That is an operational footgun, not a forgery: the record never claims a privacy status.
3. **Record-and-attest**: add the run's `private` declaration to the record schema (informational); `record-verify` checks consistency where declared — `private=true` with any successful free-tier report is ineligible, because the run itself should have refused such a seat, so its presence proves the run-time check was bypassed. Undeclared records are judged as today. This keeps the eligibility bar meaningful without assuming privacy for records that never declared it.

*Recommendation.* **Option 3** if the owner wants this property machine-checked; **Option 2** is defensible as-is. The panel's literal recommendation — blanket free-tier ineligibility in `record-verify` — should **not** be adopted: it disqualifies the owner's own panel design and every attempt in the ledger, and it mistakes the policy's purpose (data protection) for a verdict-quality bar. Either way the choice defines what a "clean record" claims, so it is the owner's to make. Until then this finding stands open as **OWNER DECISION — PENDING**; per the round's protocol, a closing attempt that blocks *solely* on this point is a clean stopping point at the owner's decision, not a round failure.

## The fixed major

**[5] `782c2c02bb16` — an explicit agent timeout was silently swapped for the default at the library seam. Fixed in 0.9.2.** Proven by executable probe, before and after (no reliance on the panel's say-so): at v0.9.1, `build_provider("agent:bot:true", agent_timeout=0)` produced a seat whose captured per-call timeout was **900** (`AGENT_TIMEOUT`) — `timeout=agent_timeout or AGENT_TIMEOUT` treats the explicit 0 as "unset"; `agent_timeout=-3` passed through verbatim to the subprocess layer, where it would fail late and confusingly; `None` → 900 by design; `5` → 5. The CLI boundary has rejected non-positive `--timeout` since v0.9.1, but the library seam (`build_provider`/`build_providers`, used by embedded callers and the bench) had not. Fix: `build_provider` now passes `AGENT_TIMEOUT` only when `agent_timeout is None`, and `command_agent` — which has exactly one caller, `build_provider`, so both builder seams are covered — normalizes `None` to the default and raises `ProviderError` at construction for `timeout <= 0`. Post-fix probe: `None` → 900, `5` → 5, `0` → `ProviderError`, `-3` → `ProviderError`. Regression tests: `tests/test_v092_fixes.py::AgentTimeoutSeamTests` (6 tests: singular, plural, and direct seams).
